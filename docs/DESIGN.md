# 设计说明与实现细节

这份文档记录 dsh-startup-splash 的内部机制、踩过的坑和诊断方法。日常使用看 [README](../README.md) 就够了。

---

## 一、启动的四段与三段

DSH 的启动不是「加载插件」一条线。实测（2026-11-17，到窗口可见共 ~17.5s）：

| 阶段 | 耗时 | 判据（真实信号） |
|---|---:|---|
| ① 启动引擎 | ~6.7s | Electron 子进程逐类出现：main / gpu-process / renderer / utility / host |
| ② 加载插件 | ~3.1s | 观察者的 `active / 预期总数`，384 个组件 |
| ③ 准备服务 | ~6.0s | 插件计数停滞 → 宿主打印 `dsh web:`；这段在等 MCP 连接与服务作用域 |
| ④ 呈现界面 | ~1.7s | `dsh web:` 出现 → `MainWindowHandle` 非 0 |

进度条只分**三段**，因为③和④在观感上都是「等」：

| 段 | 带宽 | 驱动方式 |
|---|---|---|
| ① 启动引擎 | 0 → **37%** | **整棵进程树的累计 CPU 时间**（渐近曲线，上限 36.4%） |
| ② 加载插件 | 37 → **91%** | **只用计数**：`active / 预期总数` |
| ③ 呈现界面 | 91 → **100%** | 就绪 → 窗口可见 |

### 核心原则：条只在数字动的时候动

早期版本把插件阶段压成 17% 的窄带、另一段用时间缓动去填，结果出现「数字冻结但条在爬」的观感矛盾 —— 用户一眼就看出是假的。现在统一成：**数字不动，条就停。**

阶段③那 6 秒里插件计数确实停在 380/384，所以条也停，文案改写成「正在等待服务就绪（MCP 与作用域）· 已等待 3.2s」，并让火花点做呼吸动效，表达「仍在工作」而**不延长进度条**（延长就等于假装有进度）。

### 阶段①为什么用 CPU 驱动

从宿主子进程出现（~1.6s）到观察者挂载（~6s）这 **4~5 秒里不会再出现新进程** —— 宿主在进程内加载模块，没有任何离散事件可报。**唯一真实在动的就是 CPU 时间和内存**，所以条跟着 CPU 走。

两个必须注意的细节：

- **CPU 必须算整棵进程树**：只算 `DeepSeek Harness.exe` 会漏掉 MCP 的 `python.exe` / `windows-mcp.exe` / `node.exe`，导致等待 MCP 那 6 秒 CPU 数字**完全冻结**
- **进程退出会让累计 CPU 倒退**：必须记录每个 pid 的 CPU 峰值，进程退出后保留其最终值（实测曾出现 16.2s → 15.0s 倒退）

### 明细行格式

固定顺序，所有阶段一致：**已激活 → 进程 → 服务 → CPU → 内存 → 已等待**

- `已激活` 只在开始加载插件后出现（阶段①没有计数，不显示 `0 / 0`）
- `服务` 只在有服务子进程后出现（`>0` 才显示）
- `已等待` 只在进入等待服务阶段后出现

三个可选字段是**追加**，不会插入已有字段之间。

## 二、工作原理

```
DSH 启动
   │
   ├─ ① 枚举进程树 → 累计 CPU 时间驱动进度条
   │
   ├─ observer 订阅 Cordis internal/status，每条 active 事件同步写一行 jsonl
   │     ↓
   ├─ ② splash.ps1 每 130ms 增量读 jsonl，算 active / 预期总数
   │     ↓
   ├─ splash.html 每 120ms 轮询 ui/state.json，渲染进度条与文案
   │
   └─ ③ stdout 出现 `dsh web:` = 宿主就绪 → 再等窗口可见 → 100% → 关面板
```

## 三、observer 插件

一个极小的 DSH 插件（`observer/`）：

- **只读**：只订阅事件，不 `provide`、不 `set`、不改任何 DSH 状态
- **只写**：固定写 `runtime/observer.jsonl`（用 `import.meta.url` 解析真实路径，所以从 profile 的 junction 加载也能写回项目目录）
- **异常全吞**：任何异常就地 `try/catch`，绝不影响启动
- **开销可忽略**：常开文件描述符 + `writeSync` 追加，只记 `becameActive` 迁移
- **写入即时**：事件发生到磁盘可见实测 **72 ms**

> ⚠️ 早先用「攒 32 条 + 250ms 定时器异步刷」，但插件加载期 Node 的事件循环被同步初始化工作长时间占满，**定时器根本不触发** —— 实测事件 20.75s 就发生，文件却到 28.61s 才可见，面板第一次读到就已经 327/366，进度条完全失去意义。
>
> **在启动路径上，异步批量写等于没写。**

## 四、`runtime/` 里的文件

| 文件 | 必需性 | 作用 | 删了会怎样 |
|---|---|---|---|
| `observer.jsonl` | 必需 | 观察者写的激活事件流 | 面板无进度可显示 |
| `dsh-stdout.txt` | **必需** | 宿主 stdout，**`dsh web:` 那行是就绪信号** | 无法判断程序何时起来 |
| `dsh-stderr.txt` | 诊断 | 宿主 stderr | 启动失败时看不到原因 |
| `cache-total.json` | 建议 | 上一轮组件总数，作进度分母 | 早段百分比会偏低并来回跳 |
| `cache-cpu.json` | 建议 | 上一轮累计 CPU，作阶段①分母 | 前 6 秒进度条退化成固定爬升 |
| `splash.log` | 诊断 | 每轮完整追踪与分段耗时 | 出问题没日志可查 |
| `.edge-profile-*` | 临时 | 面板的 Chromium 配置目录 | 面板关闭时自动删除 |

全部**每次启动自动重建**。

日志按轮次裁剪，只保留最近 10 轮（`$KeepRuns = 10`），容量上限约 1.25 MB。

- **插件逐个编号**（`#1` … `#384`），每行用**该次激活自己的时间戳**

## 六、踩过的坑

按踩到的顺序，都是实测确认的：

### 1. 层叠 YAML 缺末尾换行会崩启动

`cordis.patch.yml` 最后字节是 `0x27`（`'`）而非 `0x0A`，导致下一层首行粘到本层末行，**16 个插件 config 丢失、`startup failed`**。

> 所有参与层叠的 YAML 必须保证末尾换行。

### 2. 只写 `bundles` 不写 `dependencies` 会被自动清理

DSH 启动时会把「只在 bundles 里、不在 dependencies 里」的条目当作退役选择移除，junction 也一起没。

### 3. `internal/plugin` 拿不到进度

`internal/plugin` 只在 fiber **创建时**发一次；状态迁移发的是 **`internal/status`**。state 语义：`0=pending / 2=active / 3=error / 4=disposed`。

### 4. 异步批量写在启动路径上等于没写

见上面 observer 一节。

### 5. CPU 统计漏掉子进程

见阶段①的说明。

### 6. 进程退出让累计 CPU 倒退

见阶段①的说明。

### 7. `MainWindowHandle` 不是永远为 0

它只在启动后 1.5 秒内为 0（窗口未创建）。判「宿主就绪」只认 stdout 的 `dsh web:`，判「窗口出现」用它才对。

### 8. PowerShell 变量名不区分大小写

`param([string]$Target)` 与 `$script:target = 1.0` 是同一个变量，后者把路径覆盖成 `1`，`Start-Process -FilePath 1` 报「系统找不到指定的文件」。

> **不亲自跑一遍的脚本等于没写。**

### 9. 静默 `exit 0` 是最坏的失败形态

DSH 在跑时直接 `exit 0`，面板不显示、DSH 不启动，看起来却像「跑过了」。改成弹框明确提示。

### 10. Edge 的 user-data-dir 必须有但不必持久化

Chromium 强制要求，不给就动日常浏览器配置；实测一次运行产生 **190+ MB** 缓存。改为每次唯一目录、关闭即删。

### 11. Edge 新 profile 首启会弹同步登录提示

会**整屏盖住面板**。需 `--disable-sync` + `--disable-features=…,EdgeSyncPromo,msEdgeIdentityFeature`。

### 12. headless 模式不解码视频

用 `--screenshot` 截图看不到画面是**已知限制**，不是 bug；要验证请用真实窗口，或用 `--dump-dom` 诊断页看 `readyState`。

### 13. 进度条的任何视觉状态都不能暗示「已完成」

分段刻度线显得假、单向扫描光带更假，都已删。

### 14. WMI 会拖死主循环

每 400ms 用 `Get-CimInstance Win32_Process` 读子进程 CommandLine，系统忙时单次能卡 1~2 秒，日志长时间不刷新。

### 15. 全量重读拖慢循环

每 130ms 把整份 jsonl 读一遍再全量 JSON 解析，101 KB 时实测 **29.8 ms/次**。改成按字节偏移增量解析后 **0.38 ms/次，快 78 倍**。

## 七、tools/

| 脚本 | 作用 |
|---|---|
| `simulate.mjs` | **不启动任何程序**，用真实观察者数据离线推演面板每一帧会显示什么 |
| `probe-hook.mjs` | 只读分析 jsonl 的时间结构（mount 时刻、激活跨度、快照序列） |
| `write-latency.mjs` | 测「事件发生 → 文件可见」的延迟 |
| `verify-composition.mjs` | 用 dshmarket 的 `analyzeProfile()` 只读校验 profile 组合 |
| `compare-observer-cost.ps1` | A/B 量化观察者开销（临时 profile，独立端口） |
| `test-hook.ps1` | 在临时 profile 里验证观察者（`DSH_HOME` 覆盖，不碰 desktop） |

诊断面板问题时最有用的是：

```powershell
node tools\simulate.mjs 15
```

它输出「按 130ms 采样、每一帧的百分比与文案」，并检查进度有没有倒退。

## 八、已知限制

- **只能在 DSH 完全退出时用**：DSH 单实例运行，检测到已有实例会弹框提示
- **面板是 Edge app 窗口**，有系统标题栏。真要无边框得走 WebView2 SDK
- **观察到的是 Cordis fiber 激活**，不是「某个插件文件被 import」。client 侧插件（桌宠、侧边栏等）只跑在浏览器里，宿主看不到它们的 fiber
